# Learning Philosophy

## 1. Concept before syntax

Phase 1 teaches what computers do before teaching how source code expresses it.

Do not require IDE use, typing, semicolons, library installation, or compiler troubleshooting for Mikey to complete the curriculum.

## 2. Predict before reveal

Whenever practical, ask Mikey to predict the result before the machine reveals it.

This converts a game into an experiment:

**Prediction → Experiment → Observation → Explanation**

A wrong prediction is useful evidence, not failure.

## 3. Physical cause and effect

Prefer interactions where a concept can be seen or felt:

- press → response;
- wait → timing change;
- sequence → remembered sequence;
- bit pattern → number;
- rule → different outcome;
- broken rule → debug task.

## 4. One primary concept per lesson

A game may contain loops, variables, timing, state, rendering, and input handling. The lesson should still name one primary learning objective.

For example, Jackpot may internally use many concepts, but its first lesson is simply:

**INPUT → COMPUTER → OUTPUT**

## 5. PLAY / LEARN / CHALLENGE

Every mature activity should support three experiences.

### PLAY

Low-friction fun. Explanations stay out of the way.

### LEARN

The activity pauses at useful moments to expose a single concept using ordinary language and visible behavior.

### CHALLENGE

Mikey must predict, choose, diagnose, reproduce, or explain something before the activity advances.

## 6. Debugging is a core skill

Debugging is not reserved for programming lessons.

Deliberately wrong behavior can teach:

- expected versus observed behavior;
- isolating one variable;
- testing a hypothesis;
- changing one thing at a time;
- explaining evidence.

## 7. Settings before source code

Before exposing variables in source code, expose meaningful values through a child-facing settings screen.

Example:

```text
WHEEL SPEED  100%
DIRECTION    →
JACKPOT SIZE 1
```

Later, a code lesson can connect a familiar setting to a variable.

## 8. Short sessions and visible progress

Activities should be useful in short sessions. Challenges should usually be solvable in a few minutes and should not depend on long reading passages.

Progress should represent concepts demonstrated, not time spent or repetitive grinding.

## 9. Adult-guided, offline-first

Early lessons are intended to be used with a parent/mentor nearby. Phase 1 should not depend on internet access, accounts, personal data, advertising, or online social features.

## Graduation toward IDE learning

IDE learning should be based on conceptual readiness rather than age alone.

A reasonable gate is the ability to explain, with examples from the device:

- input and output;
- sequence;
- timing;
- memory;
- condition;
- state;
- bit/binary;
- bug/debugging.

At that point, expose small pieces of code that correspond to behaviors Mikey already knows.
